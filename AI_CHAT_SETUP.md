# Assistente VR

The global header **Assistente VR** button prepares one new expense, income, card, bank account, person, goal or saving from a conversation. On mobile it is an icon-only chat bubble with sparkle and opens a full-screen sheet. It never writes financial records itself. **Revisar e confirmar** opens the corresponding existing form prefilled with a new draft; only the user's Save creates the record through the canonical workspace flow. Existing records cannot be edited or deleted by assistant drafts.

- Uses OpenAI Responses API, `gpt-6-luna`, strict structured output and `store:false`.
- Requires server-only `OPENAI_API_KEY` in Sites runtime secrets. Never commit an env file or expose the key to browser code.
- Requests require authenticated identity, exact same-origin POST, owner header and a profile belonging to that owner in the saved cloud workspace.
- Sends conversation text and a limited catalog of registered types, card names/final four/currencies, account names/final four/currencies and active people names and goal names/currencies (not target or saved balances). Does not send workspace expense history, balances, card limits, passwords or profile identity fields.
- Conversation is held in the open UI only. Closing it discards the conversation. OpenAI's API data policies still apply; `store:false` is not a claim of zero retention.
- The `finance_ai_usage` table stores daily request counters only. Atomic limits: 20 requests per account and 200 requests globally per UTC day, including failed upstream requests after reservation. These limits cap requests, not a dollar budget. Configure provider billing independently.
- No shell, payments, authentication account creation, ledger deletion, edits or autonomous posting. Creating bank-account registry records is allowed only through user-reviewed forms. Unknown references and missing fields require follow-up or manual correction. Totals and dates for installment counts are calculated locally with exact cents and month-end clamping.
- The entered installment amount can be total or monthly; the review always shows the calculated total, matching the existing Despesas schema. Interest or different final installment amounts need manual review; not invented.
- Pending or newly registered local data must sync before the server catalog can recognize it.
- Mac Nuvem uses this same web feature; legacy local profiles do not gain chat automatically.

Checks: in-memory synthetic proposal tests; live synthetic structured-output API verification without posting an entry. Real profile/chat/save and mobile presentation require user acceptance testing.

## FAQ

`lib/assistant-faq.ts` contains curated help answers, including explicit feature limitations. Exact recognized help questions are answered locally without an API request or usage counter. The server also intercepts recognized FAQ questions before reserving quota. Other help questions can use AI with the same FAQ context, but must return `action:null,data:null`; they never write financial records. Unknown functionality is not invented. FAQ content is version-controlled and shared by web and Mac Nuvem.

## Superuser (web27)
Server-owned finance_roles binds initial owner only on verified Supabase email login (rodrigosouzah@hotmail.com), once to the stable owner UUID. Native device credentials inherit that stored role after the owner signs in through email. Profile names, editable workspace data and request body cannot grant roles. Future users can be added to this registry through a separately authorized administration feature; no self-service elevation exists.

Superuser can request reviewed edits/deletions of entries, incomes, cards, accounts, people, goals, savings and profile display/settings; clear a group or all active-profile financial records; download a JSON workspace backup; query exact selected-month totals by Tipo, card, currency and Brazilian bills. Clear requires typed APAGAR. Only own authenticated workspace is loaded. No passwords, keys, ownership/role changes, code execution or actual bank payments. Existing permissions for ordinary users remain new-record proposals only.

Management proposals contain compact optimistic fingerprints. Apply revalidates server identity/role, same origin, owner, revision, target and whitelisted fields, then performs a single compare-and-swap workspace save. Client refuses apply with unsynced changes/conflicts and preserves concurrent local edits. Financial legacy schedule changes explicitly warn and use the revised normal schedule. Deleting registries leaves linked transactions for correction. Linked savings prevent goal deletion until reassigned. No financial action executes directly from a model response.

Superuser model context includes exact calculated aggregates and up to60 relevant owned records (query-ranked), excluding raw import cells, password hashes and credentials. Disclosure is shown in chat. Narrow total queries are calculated locally on server without AI usage; Brazil euro estimate uses dated ECB reference, excludes fees, and reports unavailable rates explicitly. Question month is selected profile month, stated in every direct answer.

Pasted tab/semicolon/comma tables in Superuser chat use the existing local import mapping/review flow, not OpenAI. Rows remain separate and pending until explicit posting. This is structured table import, not PDF ingestion or arbitrary prose extraction. Chat does not restore uploaded backups or grant Superuser to other users.

Superuser-only attachment + button, textarea image paste and drag-and-drop support .xlsx/.csv/.tsv and PNG/JPEG/WebP images up to4MB. Spreadsheet uploads open existing local mapping review; image bytes sent only after explicit Enviar to authenticated same-origin API with server-role check. Image input verified by allowed data-URL MIME, base64, byte signature and size; no remote URL fetch. Vision request uses a dedicated strict table schema and no stored images/conversations. Up to80 separate transactions, same order and source signs; unclear/missing cells stay blank with warnings. No inference of missing dates/year, full bank account/card identifiers stripped by extraction instructions. Users review extracted rows and mapping, then explicitly post valid rows. Images consume existing AI message quota; files are not persisted in workspace or GitHub. Synthetic vision API smoke test only; no real statement uploaded by agent.

## New-account approval (web28)
After verified authentication, new identities without an existing cloud workspace receive server-owned pending access. Initial verified owner is automatically approved. Existing cloud workspaces retain access. Pending/rejected status is checked on workspace GET/PUT, assistant proposal/apply, native device credential checks/authorization and Mac connection page. Browser shows a dedicated waiting screen and polls for approval every30seconds; it does not load pending users' local workspace cache. Approval is independent of profile names, workspace JSON and Superuser role.

Only the bootstrap owner UUID (finance_roles initial-owner) may view or review /api/access-requests. Profile menu → Aprovar usuários lists verified account requests with name/email/date/status; approve or reject, rejected requests may be reconsidered. No financial payloads shown in this panel. Decisions require authenticated owner, exact origin, owner header and bounded JSON, store reviewer/time, and never grant Superuser or change financial records. No approval email is sent; users can check status on the waiting screen. Pre-existing downloaded/offline data cannot be remotely erased by this gate. No account/approval simulation was saved to production by the agent.

## Owner administration panel (web29)
Profile menu → Painel de administração replaces the approval-only dialog. Initial owner alone can approve/reject pending accounts, block/reactivate approved accounts, and grant/revoke Superuser. Access and role are independent; grant requires approved access, blocking retains data and stored role. No account deletion, profile impersonation, financial inspection or password management. Owner target is protected. UI confirmation names target email and before/after permission. Status counts, name/email search, status filters,50-user pagination and latest50 admin-history events included. Accounts appear after verified app visit, not a full Supabase unconfirmed-user directory.

Server rechecks initial-owner registry inside admin mutation, validates allowed transitions and expected status/role, and transactionally batches conditional mutation with audit insert (actor/target/time/previous/next). Financial workspace tables untouched. Future role grants do not give admin-panel permission. Online clients refresh session authorization every30s/on focus even with unsynced edits; server checks every protected API request. Revoked Superuser chat attachment/management controls clear without deleting chat history or financial records. Previously downloaded offline data cannot be remotely erased. No real permission changes or approval tests performed by agent; in-memory synthetic permission/audit tests only.
